Performance · OpenFrame server, Immich base

Three small server changes that cut wasted work

A face query now fetches one row instead of thousands, password and PIN checks no longer block the event loop, and media responses skip a redundant filesystem call. Each result below is a focused benchmark against the upstream Immich base commit, not a measurement of the whole app.

Summary

Scope

These are synthetic benchmarks on warm caches and shared machines. They show where each change removes work. They don't show an end-to-end speedup for Immich as a whole, and nothing here measured memory use, bandwidth to clients, packet loss or CPU throttling. See Methodology for the full list of limits.

What changed

ChangeFileWhy it helps on weak hardware or networks
Add LIMIT 1 to getRandomFaceperson.repository.tsThe query fetched every visible face in a group, then kept the first one. Small servers (NAS boxes, single-board computers) now skip decoding and discarding thousands of rows.
compareSync → compare for bcryptcrypto.repository.ts, auth.service.tsEach login, password change or PIN check froze the JavaScript thread while bcrypt ran. Slow CPUs freeze it for longer. Now the hash runs on a worker thread and other requests keep moving.
Drop the fs.access check before sending mediautils/file.tsExpress sendFile already reports a missing file, so the extra check was a second filesystem call per thumbnail or video request. That call costs more on slow disks and network storage.
Strip file headers on error responsesutils/file.tsWithout the early check, a missing file could return a 404 that still carried the file's long-lived Cache-Control, so browsers and proxies might cache the 404. Error responses now drop those headers.

Face query: fetch one row, not all of them

PersonRepository.getRandomFace uses executeTakeFirst(), which keeps the first row but doesn't limit the query. Without a LIMIT, PostgreSQL sent every matching face and Node decoded all of them.

      .where('asset_face.isVisible', 'is', true)
+     .limit(1)
      .executeTakeFirst();

The median dropped about 22× at 1,000 faces and about 77× at 10,000 faces. At 1 face there's no real difference, as expected. Those ratios apply to this one query, not to Immich as a whole.

About the bytes

The byte column is the size of the decoded rows serialized as JSON. It approximates how much data reached Node. It isn't the number of bytes PostgreSQL sent over the wire, and it isn't traffic to the browser or phone.

bcrypt: stop blocking the event loop

Node runs all request handling on one JavaScript thread. bcrypt.compareSync holds that thread for the whole hash, so every other request waits. bcrypt.compare runs the same hash on libuv's worker pool. All call sites in AuthService now await the result, and a failed check still rejects the login.

-   return compareSync(data, encrypted);
+   return compare(data, encrypted);

What this doesn't show

The hash costs the same CPU time as before; bcrypt cost and hash strength are unchanged. The four checks finished sooner here because the worker pool ran them in parallel on a 12-thread laptop. Under heavy load the pool can queue. This was a repository-level test, not an HTTP benchmark on low-end hardware.

Media: one fewer filesystem call per request

sendFile checked each file with fs.access before handing it to Express, which opens and stats the file anyway. The check is gone. Error responses now drop the file headers, so a missing file returns a plain 404.

-   await access(file.path, constants.R_OK);
    …
    if (canWrite) {
+     for (const header of ['Cache-Control', 'ETag', 'Last-Modified', 'Accept-Ranges',
+       'Content-Disposition', 'Content-Type', 'Content-Length', 'Content-Range']) {
+       res.removeHeader(header);
+     }
      next(new NotFoundException());

Latency was mixed. On loopback with a warm page cache, one syscall is small next to the rest of a request, and the spread between rounds was wider than the differences:

Times are per 200 requests. The removed call should matter more on spinning disks or network storage (NFS, SMB). That wasn't measured.

Public smoke test at 128 KiB/s

A temporary deployment of the patched server ran behind a Cloudflare Worker and tunnel. With curl --limit-rate 128k, it confirmed that login, upload, caching and range requests still worked. Those cheap 304 and 206 responses matter most on slow links. One sample per scenario:

RequestStatusBytesTotal timeTime to first byte
Full original download200787,2526.34 s0.35 s

8 KiB range2068,1920.39 s0.33 s

The downloaded bytes matched the uploaded file's SHA-256. Unauthenticated requests got 401, and the WebSocket upgrade returned 101.

Not a speedup

This test checks correctness. The original server wasn't run under the same conditions, so it says nothing about before and after. Immich already supported 304 and 206 responses. The test shows the change didn't break them. The temporary deployment has since been shut down.

Verification

  • 424 backend tests passed: 384 unit tests in the focused suites and 40 PostgreSQL tests for PersonRepository.
  • 2 proxy tests passed for the temporary deployment, making 426 in total. The proxy is not part of the Immich patch.
  • TypeScript checks and the production build passed.
  • A Claude Opus review found that removing fs.access let a 404 inherit the file's caching headers. That was fixed with the header stripping above, and a second review confirmed the fix.
  • The new auth tests cover rejected passwords and PINs after the async check, so a failed comparison can't let a login, PIN reset or session unlock through.

The full Immich test suite was not run.
