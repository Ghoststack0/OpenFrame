AI-assisted pull requests are welcome

Use whatever tools help you, AI included. What matters is that the change works, you can explain it, and any performance claim comes with a measurement.

Full rules in CONTRIBUTING.md

What helps most

PerformanceProfiling, removing wasted work, faster uploads and media delivery
ImplementationsFeatures that move a goal forward, like the mobile-to-desktop connection
UXClearer flows, accessibility and the redesign
TestsCoverage for changed code and regression tests

You're the author

An AI tool doesn't change who's responsible for a pull request. Before you open one:

  1. Understand it. Read every line and be ready to explain the behaviour and the trade-offs.
  2. Verify it. Run the relevant tests, lint and type checks. Say in the PR what you ran and what you didn't.
  3. Measure speed claims. Give the baseline and candidate commits, machine, software versions, workload, commands, run count and median or mean. Report regressions too.
  4. Keep compatibility. Don't break the API, the mobile apps, existing data or upstream attribution.
  5. Disclose AI use. Say in the PR template that AI tools were used and which parts they wrote.

Privacy

Never put credentials or private photo libraries in prompts, fixtures or benchmark results.

Checks to run

For web changes, from web/:

pnpm run lint
pnpm run check:svelte
pnpm run check:typescript
pnpm test

For server changes, run the focused suites you touched from server/. The Methodology page shows how the published benchmarks were run.

Performance claims

Compare both versions on the same machine with the same settings and disposable data, and alternate which runs first. Say which kind of comparison it is: against the fork's base commit, or against the latest stable Immich release. A faster query or method alone doesn't prove faster uploads or a faster app, so say what you measured and what you didn't.
